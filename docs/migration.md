# NotiHarbor 升级、凭据迁移与回滚

当前版本启动时会先对现有应用表执行 GORM schema migration，然后在事务中对网关表做版本化迁移，并对遗留敏感字段执行幂等加密升级。原有用户、消息、通道、设置和 webhook 行会保留；通道与设置中的凭据会改写为 AES-GCM 密文。

## 升级前

先把数据库备份与当前容器镜像/tag 记录下来。MySQL 使用一致性逻辑/物理备份；SQLite 请停止应用后复制数据库及其 WAL/SHM 文件，或用 SQLite backup API。验证备份可以读取。备份必须包括保存的 ENCRYPTION_KEY，但应把密钥放在独立的安全存储中。

新安装要求首次初始化时设置 INITIAL_ADMIN_PASSWORD（至少 12 个字符）。现存 root 管理员如仍使用旧默认密码 123456，启动将要求同一变量并更新该账户密码；其他账号不会被自动更改。

## 首次升级

1. 暂停流量或进入维护窗口，停止旧应用实例，避免新旧代码同时写库。
2. 完成并检查数据库备份。
3. 设置长期固定的 ENCRYPTION_KEY，启动一个新版本实例。
4. 查看启动日志和 /readyz；确认 schema 迁移、凭据加密和数据库/Redis 连接完成。
5. 验证管理登录、通道配置解密、队列投递和回调。
6. 保留升级前备份、镜像版本和同一加密密钥。

凭据迁移在 SQL 事务内运行且可重复执行；中断时重新启动会继续处理尚未加密的值。以 enc:v1: 开头的值会跳过二次加密。

## 回滚

旧版本不能读取新版本写入的 enc:v1: 敏感字段。若需要回滚，停止所有新版本实例，再同时恢复升级前数据库备份和旧镜像。只回退二进制而保留升级后的数据库，会使旧程序无法正确使用这些通道密钥。不可直接更换 ENCRYPTION_KEY：已有凭据将不能解密。

任何数据库恢复都会丢弃备份时间之后的通知、审计和其他业务数据；在制定恢复点前评估其影响。不要把恢复操作当作常规密钥轮换方案。

从 v0.3 到 v0.4 的历史手工迁移步骤只适用于对应年代的数据版本。对较新的版本请使用本指南中的备份与升级流程，不要盲目运行旧脚本。
